# Train-only SFT teacher coverage expansion

## Scope and isolation

This analysis and the v2 data build use only the `train` records and the two
train databases from the frozen M2A manifest. The loader reads validation/test
split and task-ID metadata only for leakage accounting; it does not open their
SQLite files or copy their task payloads into the generation inputs. No task
definition, database, schema, reference SQL, verifier, formal reward, Base
Agent prompt, generation configuration, or production inference path was
modified.

The existing v1 dataset and Base Agent benchmark artifacts were left in place.
The new artifacts are written under
`artifacts/sft-data-train-teacher-v2/`.

Baseline counts:

- 20 tasks attempted and formally scored; 6 successful tasks, 3/10 templates.
- 12 failures were deterministic-policy template coverage failures. The
  policy raised before emitting its next action; they were not illegal tool
  calls and no fake observation was inserted.
- 2 tasks (`constraints`) executed SQL but produced results rejected by the
  independent verifier.
- 0 reference-SQL execution failures, 0 truncated reference results, and 0
  final-answer-format failures were observed in the train-only diagnostic.
- No failure was caused by infrastructure.

The diagnostic therefore supports a train-only reference-SQL teacher as a
coverage mechanism, while not treating the reference SQL as a model-generated
trajectory or as a Base Agent result.

## Independent teacher implementation

`src/enterprise_agent_rl/reference_sql_teacher.py` defines the new policy kind
`programmatic_reference_sql_teacher` and source label
`reference_sql_teacher`. It rejects non-train `BenchmarkTask` objects at
construction time. The generation script is
`scripts/evaluation/generate_sft_teacher_v2.py`.

For each previously uncovered train task, the policy uses the shared runtime:

```text
train BenchmarkTask
  -> DataEnvironment.reset
  -> plan / required schema or dictionary lookup
  -> SQL action through DataEnvironment and SQLTool
  -> actual Observation
  -> check action over the observed SQL columns and rows
  -> finish action grounded in the checked evidence
  -> existing rewards.verify
  -> TrajectoryStore persistence
```

The `top` tasks execute their required probe before the supervised query. The
`recovery` tasks execute the historical invalid SQL first, retain its actual
error observation, and then execute the train reference SQL. No reference SQL
is written directly into an observation, and no expected answer is read from
the verifier to construct the final answer. The final answer is produced by
the environment from the successful SQL observation.

The six existing deterministic successes are reused without changing their
`deterministic_fixture_expert` provenance. The 14 uncovered tasks are generated
with `reference_sql_teacher`. The v2 examples retain a raw trajectory path,
trajectory content hash, task/template ID, source split, policy kind/version,
reward, verifier result, and source distribution. `local_llm` is not accepted
as a v2 teacher source.

real SQL tool.

## Limitations and final decision

The artifacts are now `READY_FOR_SFT_TRAINING` for the next controlled stage.
This means the train-only data gate passed; it does not mean that a model has
improved. The dataset is still small: 20 examples, two database instances,
and only two task instances per template. Fourteen examples are
programmatic/reference-SQL-supervised actions rather than diverse model
generations. SFT should therefore remain a controlled experiment with these
coverage and diversity limitations recorded.

No SFT, GRPO, rollout training, GPU job, or Base Agent configuration change
was performed in this stage.
